1 Vectorized Data

Here the vectorized approach to geospatial data is discussed. The individual items are generally referred to as shapes, geometries or features.

1.1 The simple feature Geometries (sf)

The Simple Features standard is a widely adopted model for spatial data, extending well beyond the R environment. It is important to know that the order in which the points are listed is relevant for the resulting sf except for points (but for linestrings, multilinestrings, polygons and multipolygons). Valid polygons do not self-intersect but it is OK for a linestring to self-cross. terra is able to convert all these geometries, it uses a reduced instruction set to represent them. terra is, however, capable to transform all important and frequently used sfs to SpatVectors using ‘vect()’.

The S4 (meaning terra - specific) class is SpatVector. This is the class terra uses for vectors working with simple features. In R, an S4 class is a formal class system that provides a robust framework for defining and managing objects with specific attributes and methods. 3.1.2 geometry

In our example, polygons out of a shapefile (.shp) are used. The SpatVector class might show ‘geometry: polygons’, but this includes both simple polygons and multipolygons.

The requirements are pretty strict and detailed. Normally the user is not confronted with creating the fields as shown above. terra takes care of that. Here, we hav used ‘vect’ to create a SpatVector based on the publicly available date. Please note, that terra can transform almost any known vector-formats used in geospatial data. Possible input formats are:

  • Shapefiles (.shp): A format consisting of multiple files (.shp, .shx, .dbf) for vector data storage.

  • GeoJSON (.geojson, .json): JSON format for encoding geographic data structures.

  • KML (.kml): Keyhole Markup Language for geographic data used in applications like Google Earth.

  • GPKG (.gpkg): GeoPackage, a container format for multiple layers in a single file.

  • Spatialite (.sqlite): SQLite database format for spatial data.

  • CSV with Coordinates (.csv): CSV file with coordinate columns, requiring a specified CRS.

The vect function converts them into SpatVectors.

3.1.3 dimensions

3.1.3.1 Dimensions 1: Geometry Dimension

  • Number of Features: This dimension represents the number of geometric features in the vector data. For example, if you have a vector dataset of 100 points, this dimension will be 100. In our example we only have one Feature being the Swiss border including the lakes. This is an example of multipolygons handled as polygons in terra. Every Country could be a feature.

3.1.3.2 Dimensions 2: Attribute Dimension

  • Number of Attributes: This dimension refers to the number of attributes (columns) in the attribute table associated with the geometries. Each feature (point, line, polygon) can have multiple attributes or columns representing various properties like names, IDs, or measurements. Here we only have one dimension being Switzerland. The number of inhabitants or the surface of a country could be an attribute.

3.1.4 extent

The extent shows the minimal and maximal x and y coordinates of the SpatVector.

3.1.5 source

The source displays the original file on the basis of which the SpatVector has been created.

3.1.6 coord. ref.

Geographic coordinate reference systems (CRS) identify any location on the Earth’s surface using two values: longitude and latitude. Longitude measures the angular distance east or west from the Prime Meridian, while latitude measures the angular distance north or south of the equator. Because geographic CRSs use angular measurements, distances are not represented in meters.

In geographic CRSs, the Earth’s surface is modeled as either a sphere or an ellipsoid. Spherical models, which assume the Earth is a perfect sphere, are simpler but less accurate. Ellipsoidal models, defined by the equatorial and polar radii, better represent the Earth’s shape, which is slightly flattened at the poles. The equatorial radius is about 11.5 km longer than the polar radius.

Ellipsoids are part of the CRS’s datum, which specifies the ellipsoid to use and the relationship between coordinates and locations on Earth’s surface. There are two types of datums: geocentric (like WGS84), centered on the Earth’s center of gravity, and local (like NAD83), optimized for specific locations. A geocentric datum provides a global reference, while a local datum aligns the ellipsoid with the Earth’s surface in a specific area, accounting for regional variations like mountain ranges. Both types of datums are typically based on a geoid, which represents global mean sea level.

Projected Coordinate Reference Systems (CRSs) convert the Earth’s three-dimensional surface into two-dimensional coordinates (Easting and Northing) using map projections. These CRSs are based on Cartesian coordinates with an origin, x and y axes, and linear units like meters. However, this conversion introduces distortions in properties such as area, direction, distance, and shape. Each type of projection can only preserve one or two of these properties:

  • Equal-area projections preserve area.

  • Azimuthal projections preserve direction.

  • Equidistant projections preserve distance.

  • Conformal projections preserve local shape.

There are three main types of projections:

  • Conic: Projects the Earth’s surface onto a cone, best for mid-latitude areas with minimal distortion along tangency lines.

  • Cylindrical: Projects onto a cylinder, commonly used for world maps, with distortions increasing further from the tangency.

  • Planar (Azimuthal): Projects onto a flat surface, typically used for polar regions.

Understanding the CRS of your spatial data (whether geographic or projected) is crucial for accurate spatial and geometry operations in R.

In this document, the coordinate reference system the SpatVector uses is CH1903+ also known as LV95 (EPSG coode 2056). The ESPG is a numeric code assigned to a specific CRS by the EPSG organization. It allows for standardized referencing and avoids ambiguity in specifying the CRS.

4 Operations on Vectorized Data

4.1 Changing crs and Axes and create nice Axis Labels

Here, the Swiss crs is used. It is stored in the date and retrieved using ‘pull_crs’. This function extracts the WKT version of the CRS associated to a string, number of sf/Spat* object. The Well-known text (WKT) representation of coordinate reference systems (CRS) is a is a text markup language for representing spatial reference systems and transformations between spatial reference systems. Itis the current standard used on sf and terra packages. Well-known text representation of coordinate reference systems (WKT or WKT-CRS). The formats were originally defined by the Open Geospatial Consortium (OGC) and described in their Simple Feature Access[1] and Well-known text representation of coordinate reference systems[2] specifications. 

Overwrite the value in ggplot using ‘coord_sf’ and insert the new crs as pulled using ‘pull_crs’.

Hereinafter the ESPG-codes are used when referring to a CRS. EPSG (European Petroleum Survey Group) codes are unique identifiers used to represent coordinate reference systems (CRS) and other geodetic parameters.

Here’s a concise definition and key points about EPSG codes: EPSG Code Definition An EPSG code is a 4-5 digit number that uniquely identifies a specific coordinate reference system, datum, projection, or other geodetic parameter. For example: EPSG:4326 represents WGS 84, the standard latitude/longitude system used by GPS EPSG:3857 represents Web Mercator, commonly used in web mapping applications Key Characteristics Standardization: EPSG codes provide a standardized way to refer to CRS across different GIS software and applications3. Comprehensive: The EPSG registry includes codes for projections, datums, ellipsoids, and units of measurement. Maintained: The EPSG dataset is actively maintained by the International Association of Oil & Gas Producers (IOGP) Geomatics Committee. Range: Valid EPSG codes typically range from 1024 to 327672. Usage EPSG codes are widely used in GIS software, mapping libraries, and geospatial data formats to specify the coordinate reference system of spatial data. They simplify the process of defining and transforming between different coordinate systems.

q <- ggplot(sv) +
  geom_spatvector(data = sv) +
  coord_sf(datum = pull_crs(sv)) +
  ggtitle(
    str_c(

4.3 Cropping Maps

Here we have to define a variable of type Extent. This type specifies xmin, xmax on one hand and ymin and ymax on the other. Alternatively, a named vector could be used and the ext - function does not need to be used. However in this case impossible coordinate-pairs go unnoticed. Using ext(), an error is thrown when impossible values are found: “[ext] invalid extent”.

We will use the most recent crs for Switzerland hereinafter. It is called CH1903+ (CHTRS95, Wikipedia, EPSG: 2056).

ex <- ext(
  c(xmin = 2500000, xmax = 2713000, ymin = 1170000, ymax = 13003000)
)

svC <- crop(sv, ex, ext = T)

ggplot() +

4.5 Adding Labels

It is a huge advantage of ggplot that further geoms (ggplot objects) can be plotted on top using the well established syntax. Sometimes the axis do not need to be shown. Then we do not have to specify the CRS and can simply use the void theme of ggplot.

library(ggrepel)


Ktv <- bfs_get_base_maps(
  geom = "kant",
  most_recent = T,
  format = "shp"
) |>
  vect()

ggplot(Ktv) +
  geom_spatvector(data = Ktv, aes(fill = name), show.legend = F) +
  geom_label_repel(
    data = Ktv,
    aes(label = name, geometry = geometry),
    box.padding = .4,
    stat = "sf_coordinates", # Crucial!
    force = .1,
    force_pull = 3,
    max.overlaps = 20,
    size = 3
  ) +
  coord_sf(datum = pull_crs(Ktv)) +
  theme_void()
